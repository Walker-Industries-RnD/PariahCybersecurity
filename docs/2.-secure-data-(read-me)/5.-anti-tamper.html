5. Anti Tamper

🔧 Making Debugging / Injection / Dumping Harder — the AntiTamper class

So you want to go further and make threats #2 and #3 annoying too. Pariah now ships an opt-in AntiTamper class for exactly this. It's OFF by default and you flip it on yourself, because half of it will trip over your own debugger while you're developing.

using WISecureData;

// 1. Block the easy DLL-injection routes (Windows). Do this once at startup.
AntiTamper.TryHardenAgainstInjection();

// 2. Is someone debugging me right now? (catches managed AND native debuggers)
if (AntiTamper.IsDebuggerAttached())
{
    // panic — wipe your secrets and bail
}

// 3. Or let a background watchdog do it for you. It fires ONCE the moment a
//    debugger shows up. DO NOT enable this in debug builds — it'll catch YOU.
AntiTamper.StartWatchdog(() =>
{
    myPassword.Dispose();
    Environment.FailFast("nope");
});

What each piece actually buys you:

  • TryHardenAgainstInjection() — turns on Windows' extension-point-disable mitigation, which blocks the legacy DLL-injection/hooking routes (AppInit_DLLs, cross-process SetWindowsHookEx). I deliberately did NOT enable the nuclear "only Microsoft-signed DLLs" option, because it'll happily stop your own legit native DLLs from loading and brick your app.
  • IsDebuggerAttached() — combines the CLR check with the Win32 ones, so it also catches a debugger that detached the usual PEB flag to hide.
  • StartWatchdog(...) — polls in the background and lets you wipe-and-die the instant a debugger attaches. This doubles as your "make dumping hard" move: tools like ProcDump/WinDbg that attach as debuggers get caught — and honestly, your secret is already AES-encrypted inside any dump anyway, which is the real anti-dump win.

Now the honest part, one more time: all of this is cost-raising, not a wall. A same-privilege attacker can flip a byte in the PEB so the debugger checks lie, and an admin with a kernel debugger is invisible to every one of these. If you want even more tricks, AntiCrack-DotNet is a huge grab-bag (hardware-breakpoint detection, anti-VM, module obfuscation) — but it literally labels itself "educational only" and promises nothing against privileged attackers, which tells you exactly where the ceiling is. libsodium (NSec.Cryptography / Sodium.Core) is great for guarded memory but also won't stop a debugger.

Obfuscation (ConfuserEx2)

Slapping an obfuscator like ConfuserEx2 on your build is a legit extra speed-bump, giving you symbol renaming, control-flow obfuscation, string encryption, plus its own anti-debug/anti-tamper. It genuinely makes your DLL more annoying to reverse-engineer or "map." Two honest catches, though: (1) it's obfuscation, not encryption — public tools (de4dot, ConfuserEx2 string decryptors) unpack the vanilla build, and it gets cracked routinely (it even shows up in malware that researchers then deobfuscate); the thing that actually helps is shipping a customized ConfuserEx variant, since generic deobfuscators don't know your changes. And (2) it does nothing for the memory-read attacks — a running process still decrypts everything to actually run, so obfuscation slows down understanding your code, not reading your secrets at runtime. Worth it as a layer against casual RE; not a wall.
